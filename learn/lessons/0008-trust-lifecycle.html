검토 상태와 낡은 개념

개념에 "누가 확인했나"(verified), "지금 쓸 내용인가"(status), "언제부터 낡았다고 볼까"(stale_after)를 적는다. 검색기가 고른 개념마다 신뢰 등급과 주의를 붙여 보여 주게 만든다.

약 90분회상 5 · 읽기 15 · 퀴즈 5 · 실습 50 · 검토 15용어: GLOSSARY.md · 핵심 규칙

왜 이것이 다음인가

0007에서 정책 개념이 FAQ를 보고 썼다는 것(출처)을 적었다. 출처는 "무엇을 보고 썼나"만 말한다. 정책 문장이 FAQ와 정말 같은지 누가 확인했는지, 그 확인이 아직 유효한지는 말하지 않는다. 오늘은 그 두 가지를 적고, 소비자(검색기)가 그것을 읽어 사용자에게 보여 주게 한다. 학습 계획 §6의 심화 2다.

시작 전 확인. 오늘 코드는 0003의 splitFrontmatter와 0004의 pnpm retrieve를 쓴다. 둘 다 구현되어 있다. pnpm retrieve는 오늘 --now 옵션이 생겼고, 실습 전에는 "(신뢰 표시 생략 …)" 한 줄이 붙는다.

0. 회상

FAQ 개념이 검색에서 정책 개념을 밀어낸 이유를 말하고, type으로 그것을 막는 방법을 하나 든다.

FAQ는 고객이 묻는 말투로 써서 질문과 두 글자 묶음이 많이 겹쳤고, 상한 3개 가운데 한 자리를 차지했다. type은 소비자가 라우팅과 필터링에 쓰는 값이므로§4.1, 검색 단계에서 type: Reference를 근거 후보에서 빼거나 순위를 낮출 수 있다. 오늘도 검색기는 고치지 않는다. 실습 출력에서 FAQ가 계속 1순위로 나오는 것은 이 때문이다.

정책 문장과 FAQ가 같다는 것을 사람이 확인했다. 그 사실은 개념의 어디에 적는가?

frontmatter의 verified에 { by: human:<id>, at: <시각> }로 적는다.§5.2 오늘 실습 3단계에서 직접 한다.

FAQ가 고쳐지면 정책 개념이 낡았다는 것을 소비자가 어떻게 알 수 있을까?

명세가 주는 신호는 두 가지다. 하나는 생산자가 미리 적어 둔 stale_after다. 그 시각이 지나면 낡았다고 본다.§5.5 다른 하나는 출처 쪽 시각이다. sources[].last_modified(출처가 바뀐 시각)가 개념의 verified 시각보다 늦으면 다시 확인할 때가 됐다는 뜻이다.§5.1 두 번째는 명세가 정한 판정이 아니라 소비자가 고를 수 있는 휴리스틱이다. 오늘 코드는 첫 번째만 쓴다.

1. 쓴 사람과 확인한 사람은 다르다

generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-30T14:00:00Z }   # 누가 썼나, 언제 바뀌었나
verified:
  - { by: human:kliu@acme, at: 2026-07-01T16:00:00Z }                       # 누가 확인했나, 언제
status: stable                                                              # 지금 쓸 내용인가
stale_after: 2026-12-31T00:00:00Z                                           # 이 시각부터 낡았다

공식 예제 번들의 tables/orders.md frontmatter다. 에이전트가 쓰고 사람이 확인했다. generated와 verified를 나눈 이유가 이것이다. 쓴 쪽이 확인한 쪽일 필요는 없다.§5.2

2. 명세 규칙

신뢰: generated와 verified (§5.2)

  • generated는 지금 내용이 어떻게 만들어졌는지 적는다. by는 필수이고, at은 내용이 마지막으로 의미 있게 바뀐 시각이다.
  • verified는 내용을 출처나 resource와 대조해 확인한 기록의 목록이다. 항목마다 by와 at을 쓴다. 사람의 승인과 야간 프로세스처럼 서로 독립된 확인을 여럿 적을 수 있다. "얼마나 최근인가"는 가장 늦은 at이다.
  • 둘은 따로 움직인다. 내용이 바뀌어도 다시 확인하지 않았을 수 있고, 내용을 다시 쓰지 않고 다시 확인할 수도 있다.
  • 대시 없는 매핑 하나도 쓸 수 있다. verified: { by: human:ahormati, at: … }. 소비자는 이것을 원소 하나짜리 목록으로 읽어야 한다(MUST).§5.2 §11 T1단계가 이것이다.

신뢰 등급 (§5.3)과 행위자 표기 (§7)

verified등급
키가 없다unverified
human:이 아닌 행위자만 있다machine-confirmed
human:<id> 행위자가 있다human-reviewed
  • 행위자는 세 형식이다. 에이전트·도구는 <producer>/<version>, 사람은 human:<id>, 자동 프로세스는 process:<id>.§7
  • 등급은 human: 접두사로만 정한다. 그래서 생산자는 사람이 쓰거나 확인한 내용에 반드시 이 접두사를 써야 한다(MUST).§7 거꾸로 말하면, 사람이 확인하지 않았는데 human:을 쓰면 소비자는 그대로 믿는다.
  • 등급은 권고 신호다. 접근 제어가 아니다. 신뢰 필드가 하나도 없는 개념도 읽을 수 있고, 소비자는 그것을 거부하면 안 된다(MUST NOT).§5.3
  • 빈 목록 verified: []은 명세가 따로 말하지 않는다. 이 과정은 확인 기록이 없으므로 unverified로 본다(과정 설계).

수명: status와 stale_after (§5.4·§5.5)

  • status는 draft(검토 전, 불완전할 수 있음), stable(기본, 쓸 수 있음), deprecated(링크와 기록용으로 남김, 현재 내용 아님) 중 하나다. 없으면 stable이다.§5.4 세 값이 아닌 것을 만나면 이 과정은 거부하지 않고 주의만 표시한다(과정 설계, §11의 "나머지 제약은 부드러운 안내"를 따름).
  • stale_after는 절대 시각이다. now >= stale_after이면 낡았다. "30일 뒤" 같은 상대 기간이 아니라서, 언제 읽었는지와 상관없이 단순 비교로 정해진다.§5.5 같은 시각이면 이미 낡은 것이다("on/after").
  • 소비자는 등급과 낡음을 명세가 정한 필드로만 판단한다(SHOULD).§11 예를 들어 파일 수정 시각이나 generated.at으로 낡음을 판정하지 않는다.

이 저장소에서 정직하게 적기

evaluation.md 7회차를 보면 "세 곳 모두 같다 (에이전트가 파일을 열어 대조함)"이라고 적혀 있다. 그 대조는 사람의 확인이 아니다. 지금 그 사실을 기록한다면 { by: claude-code/opus-5-5, … }이고 등급은 machine-confirmed다. human:은 여러분이 직접 파일을 열어 대조한 뒤에만 쓴다. 학습 계획도 "실제로 사람이 확인한 문서에만 verified를 기록한다"고 말한다.

모범 답안: normalizeVerified, trustTier, assess (테스트를 직접 통과시킨 뒤에 열기) 
export function normalizeVerified(value: unknown): Verification[] {
  if (value === undefined || value === null) return [];
  const list = Array.isArray(value) ? value : [value]; // 대시 없는 매핑 하나 = 원소 하나짜리 목록
  const out: Verification[] = [];
  for (const item of list) {
    if (!item || typeof item !== 'object' || Array.isArray(item)) continue;
    const o = item as Record<string, unknown>;
    if (o.by === undefined || o.by === null) continue;
    const at = dateText(o.at);
    out.push(at === undefined ? { by: String(o.by) } : { by: String(o.by), at });
  }
  return out;
}

export function trustTier(verified: Verification[]): Tier {
  if (verified.length === 0) return 'unverified';
  return verified.some((v) => v.by.startsWith('human:')) ? 'human-reviewed' : 'machine-confirmed';
}

export function assess(fm: Record<string, unknown>, now: Date): Assessment {
  const verified = normalizeVerified(fm.verified);
  const a: Assessment = { tier: trustTier(verified), status: 'stable', stale: false, cautions: [] };
  let latest = -Infinity;
  for (const v of verified) {
    const t = v.at === undefined ? NaN : Date.parse(v.at);
    if (!Number.isNaN(t) && t > latest) {
      latest = t;
      a.latestVerifiedAt = v.at;
    }
  }
  if (fm.status !== undefined && fm.status !== null) a.status = String(fm.status);
  if (a.status === 'draft' || a.status === 'deprecated') a.cautions.push(a.status);
  else if (a.status !== 'stable') a.cautions.push('unknown-status');
  const staleAfter = dateText(fm.stale_after);
  if (staleAfter !== undefined) {
    a.staleAfter = staleAfter;
    const t = Date.parse(staleAfter);
    if (Number.isNaN(t)) a.cautions.push('bad-date');
    else if (now.getTime() >= t) {
      a.stale = true;
      a.cautions.push('stale');
    }
  }
  return a;
}

5. 검토

  • 기록은 기록일 뿐이다. human:이라고 적으면 소비자는 믿는다. 확인을 하지 않은 사람이 적으면 신호가 거짓이 된다. 그래서 오늘 실습은 직접 대조한 뒤에만 적게 했다.
  • 낡음과 검토 시점은 다른 질문이다. stale_after는 생산자가 미리 정한 유효 기한이고, verified[].at은 마지막 확인 시점이다. 확인을 다시 하면 생산자가 stale_after도 뒤로 미뤄 적는 것이 자연스럽다. 명세는 둘을 묶어 두지 않는다.
  • 신호는 순위를 바꾸지 않았다. 오늘 검색기는 주의를 붙이기만 했다. 그래서 검토하지 않은 FAQ가 여전히 1순위다. 신호를 검색과 답변에 어떻게 반영할지는 5단계에서 정한 소비자 정책이고, 0009 뒤 웹 화면에서 구현할 수 있다.
  • 출처 쪽 신호도 있다. §5.1의 author, usage_count, last_modified는 출처 자체의 신뢰 신호다. 특히 usage_count는 점수가 아니라 "살아 있나, 늘고 있나"로 읽으라고 명세가 말한다.§5.1

완료 기준 (학습 계획 §6 심화 2)

  • pnpm test의 T단계 통과.
  • 직접 대조한 개념에만 verified(human:)를 적었다. pnpm validate 오류 0개.
  • 낡은 사본에서 pnpm retrieve가 stale·deprecated 주의를 붙이는 것을 보고, --now로 주의가 바뀌는 것을 확인했다.
  • 낡은·deprecated 개념을 소비자가 어떻게 다룰지 evaluation.md 8회차에 적었다.
