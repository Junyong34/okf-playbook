검토 상태와 낡은 개념

개념에 "누가 확인했나"(verified), "지금 쓸 내용인가"(status), "언제부터 낡았다고 볼까"(stale_after)를 적는다. 검색기가 고른 개념마다 신뢰 등급과 주의를 붙여 보여 주게 만든다.

v0.3 기준. 2026-11-19 OKF v0.3 기준으로 갱신했다. 명세 인용(§)은 v0.3 번호다. v0.2에서 바뀐 점은 docs/okf-v0.3-changes.md에 있다. 이 레슨이 가장 많이 바뀌었다. 신뢰 등급을 현재 검토 기록으로만 정하고, 검토 기록에 by와 at이 둘 다 있어야 하며, 읽을 수 없는 stale_after는 신선하지 않다고 본다. superseded_by도 새로 생겼다.

왜 이것이 다음인가

0007에서 정책 개념이 FAQ를 보고 썼다는 것(출처)을 적었다. 출처는 "무엇을 보고 썼나"만 말한다. 정책 문장이 FAQ와 정말 같은지 누가 확인했는지, 그 확인이 아직 유효한지는 말하지 않는다. 오늘은 그 두 가지를 적고, 소비자(검색기)가 그것을 읽어 사용자에게 보여 주게 한다. 학습 계획 §6의 심화 2다.

시작 전 확인. 오늘 코드는 0003의 splitFrontmatter와 0004의 pnpm retrieve를 쓴다. 둘 다 구현되어 있다. 시각 읽기는 공용 함수 parseTimestamp(src/okf/concept.ts)가 맡는다. pnpm retrieve는 오늘 --now 옵션이 생겼다. 지금 저장소의 pnpm retrieve·pnpm prompt·pnpm check-answer는 trust.ts를 쓰는 질의응답 모듈(src/okf/ask.ts)을 거치므로, trust.ts가 TODO인 동안에는 Error: TODO T1단계 …로 멈춘다. 실습은 테스트로 먼저 진행한다.

0. 회상

FAQ 개념이 검색에서 정책 개념을 밀어낸 이유를 말하고, type으로 그것을 막는 방법을 하나 든다.

FAQ는 고객이 묻는 말투로 써서 질문과 두 글자 묶음이 많이 겹쳤고, 상한 3개 가운데 한 자리를 차지했다. type은 소비자가 라우팅과 필터링에 쓰는 값이므로§4.1, 검색 단계에서 type: Reference를 근거 후보에서 빼거나 순위를 낮출 수 있다. 오늘도 검색기는 고치지 않는다. 실습 출력에서 FAQ가 계속 1순위로 나오는 것은 이 때문이다.

정책 문장과 FAQ가 같다는 것을 사람이 확인했다. 그 사실은 개념의 어디에 적는가?

frontmatter의 verified에 { by: human:<id>, at: <시각> }로 적는다. by와 at은 둘 다 필수다.§5.2 오늘 실습 3단계에서 직접 한다.

FAQ가 고쳐지면 정책 개념이 낡았다는 것을 소비자가 어떻게 알 수 있을까?

명세가 주는 신호는 두 가지다. 하나는 생산자가 미리 적어 둔 stale_after다. 그 시각이 지나면 낡았다고 본다.§5.5 다른 하나는 출처 쪽 시각이다. sources[].last_modified(출처가 바뀐 시각)가 개념의 verified 시각보다 늦으면 다시 확인할 때가 됐다는 뜻이다.§5.1 두 번째는 명세가 정한 판정이 아니라 소비자가 고를 수 있는 휴리스틱이다. 명세는 낡음을 stale_after로만 판단하라고 권한다(SHOULD).§11.2 오늘 코드는 첫 번째만 쓴다.

1. 쓴 사람과 확인한 사람은 다르다

generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-30T14:00:00Z }   # 누가 썼나, 언제 마지막으로 의미 있게 바뀌었나
verified:
  - { by: human:kliu@acme, at: 2026-07-01T16:00:00Z }                       # 누가 확인했나, 언제
status: stable                                                              # 지금 쓸 내용인가
stale_after: 2026-12-31T00:00:00Z                                           # 이 시각부터 낡았다

공식 예제 번들의 tables/orders.md frontmatter다. 에이전트가 쓰고 사람이 확인했다. generated와 verified를 나눈 이유가 이것이다. 쓴 쪽이 확인한 쪽일 필요는 없다.§5.2 시각도 본다. 확인(2026-07-01T16:00)이 마지막 변경(2026-06-30T14:00)보다 늦다. 그래서 이 확인은 지금 내용을 본 것이고, 등급은 human-reviewed다. 에이전트가 7월 2일에 내용을 다시 쓰고 generated.at을 올리면 같은 기록이 그대로 있어도 등급이 떨어진다. 2절에서 이유를 본다.

2. 명세 규칙

시각 형식 (§5)

  • 시각 키는 generated.at, verified[].at, stale_after, sources[].last_modified, usage_window.from·to다. 값은 RFC 3339의 두 형식뿐이다. 오프셋 있는 date-time(2026-06-30T14:00:00Z, 2026-11-18T15:00:00+09:00)은 그 순간이고, 날짜만(2026-06-30)은 그날 UTC 0시다. 그 밖의 형식은 무효다. 오프셋 없는 2026-06-30T14:00:00도 무효다.§5
  • 소비자는 따옴표 문자열과 YAML 고유 시각을 모두 받아야 한다(MUST). 생산자는 generated.at과 verified[].at에 date-time을 쓰는 편이 좋다(SHOULD). 두 값을 서로 비교하기 때문이다.
  • v0.2 처음 공개본은 날짜만 쓴 값의 시간대를 적지 않았고, 공개 뒤 본문을 고쳐 오프셋을 요구했다. v0.3은 날짜만 쓴 값을 다시 받되 "UTC 0시"라는 고정된 뜻을 붙였다.§13.2

신뢰: generated와 verified (§5.2)

  • generated는 지금 내용이 어떻게 만들어졌는지 적는다. by는 필수이고, at은 내용이 마지막으로 의미 있게 바뀐 시각이다. 서식·공백·링크 수리 같은 사소한 수정은 generated.at을 바꾸지 않는다. 소비자는 generated.at으로 검토 기록이 현재인지 가린다. 낡음은 stale_after만 정한다.
  • verified는 내용을 출처나 resource와 대조해 확인한 기록의 목록이다. 기록마다 by(행위자)와 at(시각)이 둘 다 필수이고, 하나라도 없는 기록은 소비자가 무시한다. 사람의 승인과 야간 프로세스처럼 서로 독립된 확인을 여럿 적을 수 있다. 가장 최근 확인은 가장 늦은 at이다.
  • 둘은 따로 움직인다. 내용이 바뀌어도 다시 확인하지 않았을 수 있고, 내용을 다시 쓰지 않고 다시 확인할 수도 있다.
  • 대시 없는 매핑 하나도 쓸 수 있다. verified: { by: "human:ahormati", at: … }. 소비자는 이것을 원소 하나짜리 목록으로 읽어야 한다(MUST).§5.2 null·빈 문자열·빈 목록(verified: [])은 키가 없는 것과 같다. 필수 키가 없는 항목은 무시하고 경고하는 편이 좋다(SHOULD).§11.2 T1단계가 이것이다.

신뢰 등급 (§5.3)과 행위자 표기 (§7)

검토 기록의 at이 generated.at과 같거나 늦으면, 또는 generated가 없으면 그 기록은 현재 기록이다. 소비자는 등급을 현재 기록으로만 정해야 한다(MUST).§5.3

현재 기록등급
없다 (verified가 없거나, 모두 마지막 변경 전이거나, 모두 무시됨)unverified
human:이 아닌 행위자만 있다machine-confirmed
human:<id> 행위자가 있다human-reviewed
  • 왜 현재 기록만 세는가. 에이전트가 사람 검토 뒤에 개념을 다시 쓰면, 그 사람은 새 문장을 읽지 않았다. 다시 확인하기 전까지는 human-reviewed가 아니다. 마지막 변경 전 기록은 파일에 이력으로 남고, 소비자는 "마지막 변경 전 검토"로 보여 줘도 된다(MAY).§5.3 v0.3의 깨지는 변경 두 개 가운데 하나다. 등급이 내려가기만 하므로 대체 해석은 없다.§13.1
  • 행위자는 두 형식이다. 에이전트·도구는 <producer>/<version>, 그 밖의 행위자는 <scheme>:<id>다. 명세가 정한 스킴은 human:(사람), team:(사람들의 묶음), process:(자동 프로세스)이고, 다른 스킴도 쓸 수 있지만 소비자는 사람이 아닌 것으로 본다.§7
  • 등급은 human: 스킴으로만 정한다. 그래서 생산자는 사람이 쓰거나 확인한 내용에 반드시 이 스킴을 써야 한다(MUST). team:finance-fpa는 누가 확인했는지 특정하지 않으므로 machine-confirmed다.§7 거꾸로 말하면, 사람이 확인하지 않았는데 human:을 쓰면 소비자는 그대로 믿는다.
  • 등급은 권고 신호다. 접근 제어가 아니다. 신뢰 필드가 하나도 없는 개념도 읽을 수 있고, 소비자는 그것을 거부하면 안 된다(MUST NOT).§5.3

수명: status·superseded_by와 stale_after (§5.4·§5.5)

  • status는 draft(검토 전, 불완전할 수 있음), stable(기본, 쓸 수 있음), deprecated(링크와 기록용으로 남김, 현재 내용 아님) 중 하나다. 없으면 stable이다. 목록에 없는 값은 stable이 아니다. 현재 지식만 거르는 소비자는 그 개념을 빼고, 원래 값을 보여 주는 편이 좋다(SHOULD).§5.4 우리 검색기는 빼지 않고 unknown-status 주의와 원래 값을 보여 준다.
  • superseded_by(v0.3 추가)는 status: deprecated인 개념을 대신하는 개념의 경로 하나다. deprecated일 때만 뜻이 있다. 경로 필드라서 §6 규칙으로 푼다. 현재 지식만 거르는 소비자는 이 경로를 따라가 대체 개념을 주는 편이 좋다(SHOULD). 개념을 옮기거나 이름을 바꿀 때는 옛 경로에 짧은 deprecated 개념을 남기고 superseded_by로 새 경로를 가리킨다.§5.4 공식 예는 Acme Retail metrics/gross-margin-legacy.md다.
  • stale_after는 절대 시각이다. now >= stale_after이면 낡았다. "30일 뒤" 같은 상대 기간이 아니라서, 언제 읽었는지와 상관없이 단순 비교로 정해진다. 같은 시각이면 이미 낡은 것이다("on or after"). 낡았다는 것은 "다시 확인하라"는 뜻이지 "틀렸다"는 뜻이 아니다.§5.5
  • 읽을 수 없는 stale_after는 신선하지 않다. 빈 값·null은 키가 없는 것과 같다. 하지만 값이 있는데 시각으로 읽을 수 없으면, 소비자는 그 개념을 신선하다고 보면 안 되고(MUST NOT) 형식이 잘못됐다고 보여 주는 편이 좋다(SHOULD).§5.5 우리 assess는 stale: false, fresh: false와 bad-date 주의를 낸다. "낡았다"고 단정하지도 "신선하다"고 하지도 않는다.
  • 소비자는 등급을 현재 검토 기록으로, 낡음을 stale_after로만 판단한다.§11.2 예를 들어 파일 수정 시각이나 generated.at으로 낡음을 판정하지 않는다.

이 저장소에서 정직하게 적기

evaluation.md 7회차를 보면 "세 곳 모두 같다 (에이전트가 파일을 열어 대조함)"이라고 적혀 있다. 그 대조는 사람의 확인이 아니다. 지금 그 사실을 기록한다면 { by: claude-code/opus-5-5, … }이고 등급은 machine-confirmed다. human:은 여러분이 직접 파일을 열어 대조한 뒤에만 쓴다. 학습 계획도 "실제로 사람이 확인한 문서에만 verified를 기록한다"고 말한다.

3. 기억에서 꺼내기

점수:

Q1. generated는 없고, verified에 process:nightly와 human:kim 두 기록이 있다(둘 다 by·at 있음). 등급은?

  1. unverified
  2. human-reviewed
  3. machine-confirmed
  4. 둘이 섞여서 판정할 수 없다

  2. 형식 오류로 보고한다
  3. 원소 하나짜리 목록으로 읽는다
  4. human-reviewed보다 한 단계 낮게 본다

  1. 낡았다
  2. 아직 아니다, 1초 뒤부터다
  3. generated.at을 봐야 안다
  4. status가 deprecated일 때만 낡았다

Q4. status도 verified도 없는 개념은?

  1. draft, unverified
  2. 명세 위반이므로 검색에서 뺀다
  3. deprecated, machine-confirmed
  4. stable, unverified

  2. machine-confirmed
  3. unverified
  4. 소비자가 이름을 보고 추측한다

Q6. generated: { by: claude-code/opus-5-5, at: 2026-11-19T10:00:00+09:00 }, verified: { by: human:jun, at: 2026-11-18T15:00:00+09:00 }인 개념의 등급은?

  2. machine-confirmed
  3. unverified (사람 기록은 이력으로 남는다)
  4. 파일을 거부한다

Q7. stale_after: 2026-12-01T00:00:00(오프셋 없음)인 개념을 2026-11-20에 읽었다. 소비자가 해야 할 일은?

  2. 키가 없는 것으로 본다
  3. 문서를 거부한다
  4. 신선하다고 보지 않고, 형식이 잘못됐다고 보여 준다

T1. 지금 코드는 무시한 항목 수도 세려고(bad-verified 주의, incomplete-verified 경고) 읽기를 readVerified로 나눴다. normalizeVerified는 그 결과의 기록만 돌려준다.

export function readVerified(value: unknown): VerifiedRead {
  const out: VerifiedRead = { events: [], ignored: 0 };
  for (const item of asList(value)) { // 빈 값은 없는 것, 대시 없는 매핑 하나 = 원소 하나짜리 목록 (§5.2, §11.2)
    const o = item && typeof item === 'object' && !Array.isArray(item) ? (item as Record<string, unknown>) : null;
    if (o === null || isBlank(o.by) || isBlank(o.at) || parseTimestamp(o.at) === null) {
      out.ignored++;
      continue;
    }
    out.events.push({ by: String(o.by), at: dateText(o.at)! });
  }
  return out;
}

export function normalizeVerified(value: unknown): Verification[] {
  return readVerified(value).events;
}

T2. 현재 기록을 가르는 generatedAt·isCurrent를 먼저 둔다.

export function generatedAt(fm: Record<string, unknown>): string | undefined {
  const g = fm.generated;
  if (!g || typeof g !== 'object' || Array.isArray(g)) return undefined;
  const o = g as Record<string, unknown>;
  if (isBlank(o.by) || parseTimestamp(o.at) === null) return undefined;
  return dateText(o.at);
}

export function isCurrent(v: Verification, generated?: string): boolean {
  if (generated === undefined) return true;
  const g = parseTimestamp(generated);
  const t = parseTimestamp(v.at);
  return g === null || (t !== null && t >= g);
}

export function trustTier(verified: Verification[], generated?: string): Tier {
  const current = verified.filter((v) => isCurrent(v, generated));
  if (current.length === 0) return 'unverified';
  return current.some((v) => v.by.startsWith('human:')) ? 'human-reviewed' : 'machine-confirmed';
}

T3.

export function assess(fm: Record<string, unknown>, now: Date): Assessment {
  const { events, ignored } = readVerified(fm.verified);
  const generated = generatedAt(fm);
  const a: Assessment = { tier: trustTier(events, generated), history: [], status: 'stable', stale: false, fresh: true, cautions: [] };
  if (generated !== undefined) a.generatedAt = generated;
  let latest = -Infinity;
  for (const v of events) {
    if (!isCurrent(v, generated)) {
      a.history.push(v);
      continue;
    }
    const t = parseTimestamp(v.at)!;
    if (t > latest) {
      latest = t;
      a.latestVerifiedAt = v.at;
    }
  }
  if (!isBlank(fm.status)) a.status = String(fm.status);
  if (a.status === 'draft' || a.status === 'deprecated') a.cautions.push(a.status);
  else if (a.status !== 'stable') a.cautions.push('unknown-status');
  if (a.status === 'deprecated' && typeof fm.superseded_by === 'string' && fm.superseded_by.trim() !== '') a.supersededBy = fm.superseded_by;
  const staleAfter = dateText(fm.stale_after);
  if (staleAfter !== undefined) {
    a.staleAfter = staleAfter;
    const t = parseTimestamp(fm.stale_after);
    if (t === null) {
      a.fresh = false; // 읽을 수 없는 값을 신선하다고 보지 않는다 (§5.5, §11.2 MUST NOT)
      a.cautions.push('bad-date');
    } else if (now.getTime() >= t) {
      a.stale = true;
      a.fresh = false;
      a.cautions.push('stale');
    }
  }
  if (ignored > 0) {
    a.ignoredVerified = ignored;
    a.cautions.push('bad-verified');
  }
  return a;
}

5. 검토

  • 기록은 기록일 뿐이다. human:이라고 적으면 소비자는 믿는다. 확인을 하지 않은 사람이 적으면 신호가 거짓이 된다. 그래서 오늘 실습은 직접 대조한 뒤에만 적게 했다.
  • 사람 검토는 내용이 바뀌면 효력을 잃는다. 에이전트가 번들을 계속 고쳐 쓰는 환경에서는 generated.at이 자주 올라간다. 사람이 다시 보지 않은 문장에 human-reviewed를 붙이지 않으려는 규칙이다. 그래서 생산자는 사소한 수정(서식, 링크 수리)에는 generated.at을 올리지 않는다.
  • 낡음과 검토 시점은 다른 질문이다. stale_after는 생산자가 미리 정한 유효 기한이고, verified[].at은 마지막 확인 시점이다. 확인을 다시 하면 생산자가 stale_after도 뒤로 미뤄 적는 것이 자연스럽다. 명세는 둘을 묶어 두지 않는다.
  • 신호는 순위를 바꾸지 않았다. 오늘 검색기는 주의를 붙이기만 했다. 그래서 FAQ가 여전히 1순위다. 신호를 검색과 답변에 어떻게 반영할지는 5단계에서 정한 소비자 정책이고, 0009 뒤 웹 화면에서 구현할 수 있다.
  • 출처 쪽 신호도 있다. §5.1의 author, usage_count, last_modified는 출처 자체의 신뢰 신호다. author도 §7 행위자 표기를 쓴다. 특히 usage_count는 점수가 아니라 "살아 있나, 늘고 있나"로 읽으라고 명세가 말한다.§5.1
