Lesson 0009 · 심화 3 (마지막)

같은 번들을 다른 방식으로 읽기

우리 번들을 그래프로 읽는 소비자를 하나 더 만든다. 같은 번들을 공식 시각화 도구로도 그려 보고, 두 소비자가 같은 파일을 다르게 읽는 지점을 찾는다. 마지막으로 명세 §10의 계산 검증 예제를 읽는다.

약 90분회상 5 · 읽기 15 · 퀴즈 5 · 실습 50 · 검토 15용어: GLOSSARY.md · 핵심 규칙
v0.3 기준. 2026-11-19 OKF v0.3 기준으로 갱신했다. 명세 인용(§)은 v0.3 번호다. v0.2에서 바뀐 점은 docs/okf-v0.3-changes.md에 있다. 이 레슨에서는 번들 그래프의 정의(§6.4)가 새로 생겼고, 공식 뷰어도 v0.3 새 저장소의 것으로 바꿨다. v0.2 뷰어와 갈리던 지점 가운데 두 곳은 v0.3에서 사라졌다.

왜 이것이 다음인가

지금까지 소비자를 다섯 개 만들었다. 검증기, 검색기, 프롬프트·답변 검사, 비교표, 출처 따라가기다. 모두 이 저장소의 코드다. OKF가 내세우는 것은 형식이지 도구가 아니다. 누구나 만들고 누구나 읽을 수 있어야 한다. 그렇다면 다른 사람이 만든 소비자도 우리 번들을 같은 뜻으로 읽을까? 오늘 그것을 직접 확인한다. 학습 계획 §6의 심화 3이고, 이 과정의 마지막 레슨이다.

시작 전 확인. 오늘 코드는 개념 읽기 모듈(src/okf/concept.ts)의 readBundle·toConcept, 0003의 resolveLink, 0007에서 쓴 경로 필드 함수 pathFields·resolvePathField를 쓴다. 모두 구현되어 있다. 공식 뷰어를 돌리려면 Git과 Python 3.11 이상이 필요하다. uv가 있으면 더 쉽다. 그래프를 브라우저에 그리려면 CDN(jsdelivr)에 접속할 수 있어야 한다. 회사망에서 막히면 실습 3단계의 대안을 쓴다.

0. 회상

에이전트가 대조한 사실과 내가 대조한 사실을 verified에 각각 어떻게 적고, 등급은 각각 무엇인가? 그 뒤 에이전트가 문장을 고쳐 쓰면 등급은 어떻게 되는가?

에이전트는 { by: claude-code/opus-5-5, at: … }로 적고 machine-confirmed다. 나는 { by: human:<id>, at: … }로 적고 human-reviewed다.§7 human만 쓰고 :<id>를 빼면 human: 스킴이 아니므로 machine-confirmed가 된다. 에이전트가 문장을 고치고 generated.at을 올리면 두 기록 모두 현재 기록이 아니게 되어 unverified로 떨어진다. 기록은 "마지막 변경 전 검토" 이력으로 남는다.§5.3 실습 5단계에서 공식 도구로도 등급을 확인한다.

stale_after를 "30일" 같은 상대 기간이 아니라 절대 시각으로 정한 이유는? 날짜만 쓴 값은 어느 순간인가?

낡았는지를 단순 비교로 정하기 위해서다. 언제 읽었는지나 언제 받았는지를 따로 알 필요가 없다.§5.5 날짜만 쓴 2026-10-01은 그날 UTC 0시다.§5 v0.2 시절에는 명세가 이것을 정하지 않아 v0.2 뷰어와 우리 소비자의 답이 갈렸다. 오늘은 v0.3 뷰어가 정말 같은 답을 내는지 확인한다.

지금 CLI 출력에서 개념 사이의 링크와 출처, 대체 관계는 어떻게 보이는가?

흩어져 있다. 링크는 pnpm retrieve의 링크 확장에서 한 단계만 보이고, 출처는 pnpm trace에서 한 개념부터 따라갈 때만 보이고, 대체 개념은 pnpm retrieve의 주의 줄에만 보인다. 번들 전체에서 누가 누구를 가리키는지 한눈에 보는 출력은 아직 없다. 오늘 만드는 pnpm graph가 그 역할을 한다.

2. 명세가 정한 그래프와 공식 뷰어

번들 그래프 (§6.4, v0.3 추가)

v0.3은 번들 그래프를 정의한다. 방향 있는 간선이 두 종류다.§6.4

  • 링크: 개념에서 번들 안 개념으로 가는 본문 링크. #fragment를 뺀 대상이 개념 파일로 풀릴 때만 개념을 가리키는 링크다. asset, 디렉터리, type 없는 .md로 가는 링크도 유효하지만 개념을 가리키지는 않는다.§6.1
  • 경로 필드: 개념으로 풀리는 경로 필드(resource, sources[].resource, superseded_by, computation, executor.resource, attester.resource). 필드를 가진 개념에서 대상으로 간다.§6.2 0007의 출처 간선과 0008의 superseded_by가 여기에 든다.
  • 끊어진 링크도 받아야 한다(MUST). 대상이 번들에 없는 링크는 잘못된 것이 아니라 아직 아무도 쓰지 않은 지식일 수 있다.§6.1 그래서 buildGraph는 개념을 가리키지 않는 참조를 간선으로 만들지 않되 버리지도 않고 dangling에 남긴다(번들에 없음 missing, 개념이 아님 not-a-concept).
  • v0.2 대체 해석은 경로 필드에만 쓴다. 본문 링크에는 쓰지 않는다.§12.1 그렇게 찾은 간선에는 legacy: true가 붙는다.
  • 명세는 간선 종류(참조, 의존 등)를 정하지 않는다. 링크는 종류 없는 관계다. 우리 그래프는 경로 필드 간선을 필드마다 나눠(source, superseded-by, executor 등) 표시한다. 그것은 이 과정의 설계다.

공식 뷰어가 하는 일

reference_agent visualize는 번들 하나를 HTML 파일 하나로 만든다. 서버도 설치도 필요 없고, 번들을 생성할 때 JSON으로 파일 안에 넣어 둔다. 그래프는 Cytoscape.js, 본문은 marked로 그리는데 둘 다 CDN에서 불러온다. README는 뷰어도 소비자의 개념 증명이라고 다시 말한다.README Visualize

  • 그래프: 개념마다 노드가 하나다. 색은 type으로 정하고, 간선은 본문의 링크로만 그린다. v0.3 뷰어는 / 시작 링크와 상대 링크를 둘 다 푼다.

명세 §10: 계산 검증 (읽기만)

표·지표 문서로 넘어가면 "이 숫자를 어떻게 계산했나"가 중요해진다. §10은 승인된 계산 방법 자체를 type: Attested Computation 개념으로 둔다. 그래서 소비자는 에이전트가 계산식을 즉석에서 지어내지 않고 승인된 계산을 돌렸는지 확인할 수 있다. OKF는 계산과 확인 방법을 기록만 하고, 직접 실행하지 않는다.§10

  • 계약 필드 (§10.2)
    • runtime: 이 타입에서는 필수다. 어떻게 실행하는지, 그리고 parameters가 무슨 뜻인지를 정한다.
    • parameters: 에이전트가 채워도 되는 이름 있는 빈칸이다. 각 항목은 { name, type, required }로 쓴다. name과 type은 필수이고, required는 없으면 false다.
    • computation: 계산을 담은 파일의 경로다. 쓰지 않으면 본문 Computation 절의 첫 코드 블록이 계산이다(§10.3).
    • executor: 실행 방법(resource)과, 실행이 돌려줄 증빙 필드(receipt)다.
    • attester: 증빙을 받아 판정을 내리는 결정적 코드(resource)다. LLM을 쓰지 않는다.
    computation, executor.resource, attester.resource는 경로 필드다. 대상이 개념이면 번들 그래프의 간선이다.§10.2
  • 에이전트는 값만 넣는다. 선언된 parameters에 값을 넣을 수는 있다(MAY). 계산식을 쓰거나 고치면 안 된다(MUST NOT).§10.3
  • 소비자의 흐름 (§10.5, 참고용): 찾기(frontmatter를 훑어 type: Attested Computation) → 불러오기 → 값 넣기 → 실행 → 판정(최소 ok, 선택 reason) → 게이트. 마지막 게이트는 판정에 실패한 값을 보여 주지 않는 단계다. now >= stale_after이면 경고하거나 값을 보여 주지 않는다.§10.5
  • verified와 판정은 다르다. verified는 정의가 아직 정책과 맞는지를 확인한다. 문서 단위이고, 느리고, 번들에 기록된다. 판정은 한 번의 실행이 승인된 방식으로 값을 만들었는지를 확인한다. 호출마다 하고, 번들에 저장하지 않는다.§10.6

실행과 판정은 이 과정의 범위 밖이다(MISSION.md). 오늘은 예제를 읽고 구조만 짚는다.

점수:

Q1. 공식 저장소의 뷰어에 대해 README가 말하는 것은?

  1. OKF를 읽는 표준 구현이다
  2. 뷰어가 그리지 못하면 번들이 틀린 것이다
  3. 소비자의 한 가지 예(개념 증명)일 뿐이다
  4. 번들에 반드시 viz.html을 넣어야 한다

Q2. Attested Computation에서 에이전트가 해도 되는 일은?

  1. 더 빠른 SQL로 고쳐 쓴다
  2. 선언된 parameters에 값을 넣는다
  3. attester 코드를 바꾼다
  4. receipt 필드를 줄인다

Q3. verified와 판정(attestation)의 차이로 맞는 것은?

  1. 둘은 같은 것을 두 번 적는다
  2. 판정은 번들에 기록되고 verified는 런타임에만 있다
  3. human-reviewed면 판정이 필요 없다
  4. verified는 정의를, 판정은 한 번의 실행을 확인한다

Q4. 공식 뷰어 그래프에서 references/returns-faq.md는 어떻게 보일까? (README 설명으로 예측)

  1. 간선 없이 떨어진 노드
  2. returns.md에서 오는 점선 간선
  3. 그래프에 나오지 않는다
  4. 모든 개념과 이어진 중심 노드

Q5. returns.md 본문에서 frontmatter가 없는 references/README.md로 링크했다. v0.3 번들 그래프에서 이 링크는?

  1. 링크 간선이다
  2. 끊어진 링크라서 번들이 적합하지 않다
  3. 간선이 아니다. 개념을 가리키지 않는 링크다
  4. README.md가 type: Unknown 개념이 된다

Q6. return-exceptions.md(deprecated)에 superseded_by: returns.md를 적었다. 번들 그래프의 간선은?

  1. 없다. frontmatter 값은 간선이 아니다
  2. return-exceptions.md → returns.md
  3. returns.md → return-exceptions.md
  4. deprecated 개념은 그래프에서 빠진다

export function buildGraph(bundle: Bundle): Graph {
  // 번들을 한 번 읽어 개념과 경로 필드를 같은 파싱 결과에서 꺼낸다.
  const read = readBundle(bundle).flatMap((file) => {
    const c = toConcept(file); // index.md·log.md·개념이 아닌 파일은 null
    return c === null ? [] : [{ file, c }];
  });
  const nodes = read.map(({ c }) => ({ path: c.path, type: c.type, title: c.title }));
  const has = new Set(nodes.map((n) => n.path));
  const edges: GraphEdge[] = [];
  const dangling: DanglingRef[] = [];
  const warnings: string[] = [];
  const seen = new Set<string>();
  const add = (from: string, raw: string, kind: EdgeKind, to: string | null, legacy = false) => {
    if (to === null) {
      warnings.push(`${from}의 ${KIND[kind]} ${raw}가 번들 밖을 가리켜 그리지 않는다.`);
      return;
    }
    const key = `${from}\n${to}\n${kind}`;
    if (to === from || seen.has(key)) return; // 자기 자신, 같은 (from, to, kind)는 건너뛴다
    seen.add(key);
    if (has.has(to)) edges.push(legacy ? { from, to, kind, raw, legacy: true } : { from, to, kind, raw });
    else {
      const exists = bundle.has(to) || bundle.has(`${to.replace(/\/$/, '')}/index.md`);
      dangling.push({ from, to, kind, raw, reason: exists ? 'not-a-concept' : 'missing' });
    }
  };
  for (const { file, c } of read) {
    for (const raw of file.links) add(file.path, raw, 'link', resolveLink(file.path, raw));
    for (const f of pathFields(c.frontmatter)) {
      const r = resolvePathField(bundle, file.path, f.value);
      add(file.path, f.value, FIELD_KIND[f.field], r.target, r.legacy);
    }
  }
  return { nodes, edges, dangling, warnings };
}

const ORDER: EdgeKind[] = ['link', 'source', 'superseded-by', 'resource', 'computation', 'executor', 'attester'];

export function backlinks(graph: Graph, path: string): { from: string; kind: EdgeKind }[] {
  return [...graph.edges, ...graph.dangling]
    .filter((e) => e.to === path)
    .map((e) => ({ from: e.from, kind: e.kind }))
    .sort((a, b) => a.from.localeCompare(b.from) || ORDER.indexOf(a.kind) - ORDER.indexOf(b.kind));
}

FIELD_KIND(경로 필드 이름 → 간선 종류)와 KIND(출력용 한국어 이름)는 파일 위쪽에 제공된다. v0.2 기준 답안과 다른 곳: sources만이 아니라 모든 경로 필드를 pathFields 순서(resource → sources → superseded_by → …)로 보고, resolvePathField로 v0.2 대체 해석을 받으며, 개념이 아닌 대상은 broken 표시가 붙은 간선이 아니라 dangling으로 뺀다.

5. 검토

  • 기준은 명세이고, 도구는 해석이다. 공식 뷰어도 소비자 하나일 뿐이다. v0.2에서 두 소비자가 갈린 (가)와 (나)는 명세가 열어 둔 곳이었다. v0.3은 그 두 곳을 닫았다. 링크와 경로 필드에 하나의 해석 규칙을 두고, 날짜만 쓴 값의 뜻을 정했다. 그러자 v0.3 뷰어와 우리 소비자가 같은 답을 냈다. 명세가 정확해지면 소비자 차이가 줄어든다. 그래도 생산자가 분명한 형식(오프셋 있는 시각, human:<id>, 개념에는 type)으로 쓰는 편이 어떤 소비자에서든 안전하다.
  • 명세가 정한 그래프와 그림에 그리는 그래프는 다를 수 있다. §6.4는 출처와 superseded_by도 번들 그래프의 간선이라고 정했다. 공식 뷰어는 여전히 본문 링크만 그린다. 그림에 무엇을 그릴지는 소비자가 정한다. 우리는 경로 필드 간선을 점선으로 나눠 그렸다. 그래서 FAQ가 출처로만 이어져 있다는 것(0007)과 대체 관계(0008)가 한눈에 보였다.
  • 도구도 명세와 어긋날 수 있다. (마)에서 공식 뷰어는 type 없는 파일을 노드로 그렸다. 공식 저장소의 코드라도 명세의 규칙(§3.2)이 기준이다. 어긋남을 찾으면 공식 저장소 Issues에 알릴 수 있다(RESOURCES.md).
  • 검색은 소비자마다 다르다. 공식 뷰어의 검색 상자는 사람이 개념을 찾는 도구라서 이름과 태그만 본다. 우리 검색기는 모델에 넘길 근거를 찾는 도구라서 본문까지 본다. 같은 번들이라도 목적이 다르면 읽는 필드가 다르다. description을 고르는 용도로 쓴다는 §4.1이 여기서도 맞는다.
  • 계산은 기록과 실행이 나뉜다. §10은 번들에 계약만 남기고, 실행과 판정은 소비자가 한다. 0008의 verified가 정의를 확인한다면, 판정은 한 번의 실행을 확인한다.
