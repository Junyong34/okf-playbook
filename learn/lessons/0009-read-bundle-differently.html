Lesson 0009 · 심화 3 (마지막)

같은 번들을 다른 방식으로 읽기

우리 번들을 그래프로 읽는 소비자를 하나 더 만든다. 같은 번들을 공식 시각화 도구로도 그려 보고, 두 소비자가 같은 파일을 다르게 읽는 지점을 찾는다. 마지막으로 명세 §10의 계산 검증 예제를 읽는다.

약 90분회상 5 · 읽기 15 · 퀴즈 5 · 실습 50 · 검토 15용어: GLOSSARY.md · 핵심 규칙

왜 이것이 다음인가

지금까지 소비자를 다섯 개 만들었다. 검증기, 검색기, 프롬프트·답변 검사, 비교표, 출처 따라가기다. 모두 이 저장소의 코드다. OKF가 내세우는 것은 형식이지 도구가 아니다. 누구나 만들고 누구나 읽을 수 있어야 한다. 그렇다면 다른 사람이 만든 소비자도 우리 번들을 같은 뜻으로 읽을까? 오늘 그것을 직접 확인한다. 학습 계획 §6의 심화 3이고, 이 과정의 마지막 레슨이다.

시작 전 확인. 오늘 코드는 0004의 readConcepts, 0003의 resolveLink, 0007의 readProvenance·classifyResource를 쓴다. 모두 구현되어 있다. 공식 뷰어를 돌리려면 Git과 Python 3.11 이상이 필요하다. uv가 있으면 더 쉽다. 그래프를 브라우저에 그리려면 CDN(jsdelivr)에 접속할 수 있어야 한다. 회사망에서 막히면 실습 3단계의 대안을 쓴다.

0. 회상

에이전트가 대조한 사실과 내가 대조한 사실을 verified에 각각 어떻게 적고, 등급은 각각 무엇인가?

에이전트는 { by: claude-code/opus-5-5, at: … }로 적고 machine-confirmed다. 나는 { by: human:<id>, at: … }로 적고 human-reviewed다.§7 human만 쓰고 :<id>를 빼면 접두사 human:이 없으므로 machine-confirmed가 된다. 실습 5단계에서 공식 도구로도 이것을 확인한다.

stale_after를 "30일" 같은 상대 기간이 아니라 절대 시각으로 정한 이유는?

낡았는지를 단순 비교로 정하기 위해서다. 언제 읽었는지나 언제 받았는지를 따로 알 필요가 없다.§5.5 그런데 "절대 시각"이라고 하면 2026-10-01처럼 날짜만 쓴 값은 어떻게 볼까? 오늘 두 소비자의 답이 갈린다.

지금 CLI 출력에서 개념 사이의 링크와 출처는 어떻게 보이는가?

흩어져 있다. 링크는 pnpm retrieve의 링크 확장에서 한 단계만 보이고, 출처는 pnpm trace에서 한 개념부터 따라갈 때만 보인다. 번들 전체에서 누가 누구를 가리키는지 한눈에 보는 출력은 아직 없다. 오늘 만드는 pnpm graph가 그 역할을 한다.

1. 형식은 하나, 소비자는 여럿

공식 저장소 README는 OKF를 특정 에이전트나 프레임워크에 묶이지 않는 형식이라고 소개한다. 누구나 만들 수 있고(사람이 손으로, 에이전트가, 카탈로그 내보내기가), 누구나 읽을 수 있다(정적 파일 서버, Obsidian 같은 지식 도구, LLM 컨텍스트, 검색 색인, 그래프 뷰어). 저장소에 들어 있는 에이전트와 뷰어는 각각 생산자와 소비자의 개념 증명(proof of concept)일 뿐이다. 기여하는 것은 형식 자체라고 말한다.README

2. 공식 뷰어가 하는 일

reference_agent visualize는 번들 하나를 HTML 파일 하나로 만든다. 서버도 설치도 필요 없고, 번들을 생성할 때 JSON으로 파일 안에 넣어 둔다. 그래프는 Cytoscape.js, 본문은 marked로 그리는데 둘 다 CDN에서 불러온다.README Visualize

명세 §10: 계산 검증 개념 (읽기만)

표·지표 문서로 넘어가면 "이 숫자를 어떻게 계산했나"가 중요해진다. §10은 승인된 계산 방법 자체를 type: Attested Computation 개념으로 둔다. 그래서 소비자는 에이전트가 계산식을 즉석에서 지어내지 않고 승인된 계산을 돌렸는지 확인할 수 있다. OKF는 계산과 확인 방법을 기록만 하고, 직접 실행하지 않는다.§10

  • 계약 필드 (§10.2)
    • runtime: 이 타입에서는 필수다. 어떻게 실행하는지, 그리고 parameters가 무슨 뜻인지를 정한다.
    • parameters: 에이전트가 채워도 되는 이름 있는 빈칸이다. 각 항목은 { name, type, required }로 쓴다.
    • executor: 실행 방법(resource)과, 실행이 돌려줄 증빙 필드(receipt)다.
    • attester: 증빙을 받아 판정을 내리는 결정적 코드다. LLM을 쓰지 않는다.
  • 에이전트는 값만 넣는다. 선언된 parameters에 값을 넣을 수는 있다(MAY). 계산식을 쓰거나 고치면 안 된다(MUST NOT).§10.3
  • 소비자의 흐름 (§10.5, 참고용 규정): 찾기 → 불러오기 → 값 넣기 → 실행 → 판정 → 게이트. 마지막 게이트는 판정에 실패한 값을 보여 주지 않는 단계다. now >= stale_after이면 경고하거나 거부한다.
  • verified와 판정은 다르다. verified는 정의가 아직 정책과 맞는지를 확인한다. 문서 단위이고, 느리고, 번들에 기록된다. 판정은 한 번의 실행이 승인된 방식으로 값을 만들었는지를 확인한다. 호출마다 하고, 번들에 저장하지 않는다.§10.6

실행과 판정은 이 과정의 범위 밖이다(MISSION.md). 오늘은 예제를 읽고 구조만 짚는다.

모범 답안: buildGraph와 backlinks (테스트를 직접 통과시킨 뒤에 열기) 
export function buildGraph(bundle: Bundle): Graph {
  const concepts = readConcepts(bundle);
  const nodes = concepts.map((c) => ({ path: c.path, type: c.type, title: c.title }));
  const has = new Set(nodes.map((n) => n.path));
  const edges: GraphEdge[] = [];
  const warnings: string[] = [];
  const seen = new Set<string>();
  const add = (from: string, raw: string, kind: EdgeKind) => {
    const to = resolveLink(from, raw);
    if (to === null) {
      warnings.push(`${from}의 ${kind === 'link' ? '링크' : '출처'} ${raw}가 번들 밖을 가리켜 그리지 않는다.`);
      return;
    }
    const key = `${from}\n${to}\n${kind}`;
    if (to === from || seen.has(key)) return;
    seen.add(key);
    edges.push({ from, to, kind, raw, broken: !has.has(to) });
  };
  for (const c of concepts) {
    for (const raw of c.links) add(c.path, raw, 'link');
    for (const s of readProvenance(bundle, c.path)?.sources ?? []) {
      if (s.resource && classifyResource(s.resource) === 'path') add(c.path, s.resource, 'source');
    }
  }
  return { nodes, edges, warnings };
}

export function backlinks(graph: Graph, path: string): { from: string; kind: EdgeKind }[] {
  const order: Record<EdgeKind, number> = { link: 0, source: 1 };
  return graph.edges
    .filter((e) => e.to === path)
    .map((e) => ({ from: e.from, kind: e.kind }))
    .sort((a, b) => a.from.localeCompare(b.from) || order[a.kind] - order[b.kind]);
}

5. 검토

  • 기준은 명세이고, 도구는 해석이다. 공식 뷰어도 소비자 하나일 뿐이다. 두 소비자가 갈린 (가)와 (나)는 모두 명세가 열어 둔 곳이다. 하나는 경로 형식을 셋 다 허용한 부분이고, 다른 하나는 날짜만 쓴 값을 정하지 않은 부분이다. 생산자가 가장 분명한 형식(상대 경로, 오프셋 있는 시각, human:<id>)으로 쓰면 어떤 소비자든 같은 뜻으로 읽는다. 팀 규칙은 그래서 필요하다.
  • 무엇을 간선으로 볼지는 소비자가 정한다. 우리는 출처도 간선으로 그렸고, 공식 뷰어는 링크만 그렸다. 명세에 따르면 출처가 번들 안 개념을 가리키면 그래프에 계보 간선이 이미 있는 것이다(§5.1). 다만 그것을 그림에 그릴지는 정하지 않는다. 그래프로 보니 FAQ가 출처로만 이어져 있다는 것(0007)이 한눈에 보였다.
  • 검색은 소비자마다 다르다. 공식 뷰어의 검색 상자는 사람이 개념을 찾는 도구라서 이름과 태그만 본다. 우리 검색기는 모델에 넘길 근거를 찾는 도구라서 본문까지 본다. 같은 번들이라도 목적이 다르면 읽는 필드가 다르다. description을 고르는 용도로 쓴다는 §4.1이 여기서도 맞는다.
  • 계산은 기록과 실행이 나뉜다. §10은 번들에 계약만 남기고, 실행과 판정은 소비자가 한다. 0008의 verified가 정의를 확인한다면, 판정은 한 번의 실행을 확인한다.
