Lesson 0007 · 심화 1

원문으로 거슬러 올라가기

정책 개념에 sources와 각주를 달아 FAQ 원문과 잇는다. 답변 → 정책 → FAQ까지 따라가 보고, 원문 개념을 번들에 넣었을 때 검색이 어떻게 바뀌는지 확인한다.

약 90분회상 5 · 읽기 15 · 퀴즈 5 · 실습 50 · 검토 15용어: GLOSSARY.md · 핵심 규칙
v0.3 기준. 2026-11-19 OKF v0.3 기준으로 갱신했다. 명세 인용(§)은 v0.3 번호다. v0.2에서 바뀐 점은 docs/okf-v0.3-changes.md에 있다.

왜 이것이 다음인가

5회차에 답변의 문장마다 인용을 붙였다. 인용은 답변이 개념을 가리킨다. 그런데 그 개념은 무엇을 보고 썼을까? 개념이 자료를 가리키는 것이 출처다. 오늘은 출처를 달아 "근거의 근거"를 따라갈 수 있게 만든다. 학습 계획 §6의 심화 1이고, 미뤄 둔 FAQ 실습도 여기서 한다.

시작 전 확인. 오늘 코드는 0003의 splitFrontmatter·resolveLink(지금은 src/okf/concept.ts에 있고, 경로 필드용 resolvePathField가 이것을 쓴다)와 0006의 pnpm compare를 쓴다. 모두 구현되어 있다.

0. 회상

0006 표에서 링크 확장이 불필요한 개념을 더한 이유를 §6.1의 문장 하나로 설명한다.

링크는 관계가 있다는 사실만 담고, 관계의 종류는 주변 문장이 전한다.§6.1 검색기는 주변 문장을 보지 않고 모든 링크를 똑같이 따라갔다.

description에만 있는 단어가 검색을 살린 사례를 들고, 그 단어를 본문에도 넣어야 하는지 판단한다.

q7의 "기간"이다. 답에 필요한 사실("3~5일")은 이미 본문에 있으므로 꼭 넣을 필요는 없다. description은 개념을 고르는 데 쓰는 요약이고§4.1, 근거는 본문에서 온다. 다만 본문만 보는 소비자를 생각하면 본문 제목에 넣는 것도 방법이다. 정답은 하나가 아니다.

답변의 근거가 번들의 개념이라면, 그 개념이 옳다는 근거는 어디에 적어 두는가?

개념의 frontmatter sources와 본문 각주다.§5.1 오늘의 주제다.

1. 인용과 출처는 방향이 다르다

답변 문장 ──인용──▶ 정책 개념 ──각주·sources──▶ FAQ 개념
"7일 이내…" [policies/returns.md]   [^returns-faq] → /references/returns-faq.md
  • 인용은 답변이 개념을 가리킨다. 5회차에 만들었다.
  • 출처는 개념이 자기를 만든 자료를 가리킨다. 오늘 만든다. 자료는 번들 밖(URL)일 수도 있고 번들 안 개념일 수도 있다.§5.1

2. 명세 규칙

sources 항목 (§5.1)

sources:
  - id: returns-faq                       # 선택. 본문이 인용하면 있어야 한다(SHOULD)
    resource: /references/returns-faq.md  # 항목 안에서 필수
    title: 반품·환불 FAQ                    # 선택
  • resource만 필수다. 따라갈 수 있는 것(절대 URL이나 번들 안 경로)이거나, 따라갈 수 없는 범위 설명(예: "BigQuery 프로젝트 X의 모든 쿼리")이다.§5.1 resource가 없는 항목은 소비자가 무시하고 경고하는 편이 좋다(SHOULD).§11.2
  • 항목 하나는 대시 없이 써도 된다. sources: { id: …, resource: … }처럼 매핑 하나만 쓰면 소비자는 항목 하나짜리 목록으로 읽어야 한다(MUST). null·빈 문자열·빈 목록은 키가 없는 것과 같다.§11.2 제공 함수 readProvenance가 이렇게 읽는다(P0단계).
  • sources[].resource는 경로 필드다. 경로 필드는 resource, sources[].resource, superseded_by, §10의 computation·executor.resource·attester.resource다.§6.2 해석 규칙은 본문 링크와 같다. URI 스킴이 있으면 절대 URL, /로 시작하면 번들 루트 기준, 그 밖은 그 파일이 있는 디렉터리 기준이다. 번들 루트 밖으로 나가는 값은 외부이고 로컬 파일 시스템에서 읽지 않는다.§6
  • v0.2 대체 해석이 있다. v0.2 명세는 경로 필드의 상대 경로가 어디 기준인지 적지 않았고, 예제는 references/x.md처럼 번들 루트 기준으로 썼다. v0.3에서 이 값은 파일 디렉터리 기준으로 풀려 찾지 못한다. 그래서 / 없는 경로 필드가 파일 기준으로 풀리지 않고, 번들이 okf_version 0.2 이하를 선언했거나 선언이 없으면 번들 루트 기준으로 다시 찾아도 된다(MAY).§6.2 §12.1 본문 링크에는 이 대체 해석이 없다. 우리 번들은 okf_version: "0.3"이라 대체 해석을 쓰지 않는다.
  • references/는 관례다. 외부 자료의 사본, 실행 안내, 코드를 두는 디렉터리 이름이다. 필수는 아니고, 다른 개념이 들어가도 된다.§6.3

문장 단위 출처: 각주 (§5.1)

할인 상품을 포함해 수령 후 7일 이내에 반품을 신청할 수 있다.[^returns-faq]

[^returns-faq]: 반품·환불 FAQ
  • 각주 라벨이 sources[].id와 같아야 한다. 라벨이 출처로 가는 열쇠다. 소비자는 각주 문장이 아니라 같은 id의 항목으로 출처를 찾는다.
  • 위치 번호(sources[0])를 쓰지 않는다. 에이전트가 문서를 계속 고쳐 쓰므로 목록 순서가 바뀌면 번호는 조용히 엉뚱한 출처를 가리킨다. id는 순서가 바뀌어도 남는다.§5.1
  • 출처가 번들 안 개념이면 계보가 이어진다. OKF에는 계보 전용 필드가 없다. 개념으로 풀리는 경로 필드는 그 자체로 번들 그래프의 간선이고, 소비자는 그 개념의 sources로 다시 따라갈 수 있다(MAY).§5.1 §6.4 오늘 만드는 trace가 이 일을 한다. 대상 파일에 type이 없으면 개념이 아니므로 따라가지 않는다.§3.2

팀 규칙을 어디까지 적용할까

0002에서 "번들 안 링크는 상대 경로로 쓴다"는 팀 규칙을 정했다(docs/team-rules.md). 이유는 GitHub와 에디터 미리보기가 본문의 / 링크를 저장소 루트로 해석해 깨뜨리기 때문이었다. 학습 계획은 resource: /references/returns-faq.md처럼 번들 루트 기준 경로를 쓴다. frontmatter 값은 미리보기에서 링크로 그려지지 않는다. 이 규칙을 sources[].resource에도 적용할지 실습 4단계에서 정한다. 어느 쪽을 고르든 / 없이 references/returns-faq.md라고만 쓰면 안 된다. v0.3에서는 policies/references/returns-faq.md로 풀린다. 번들 루트 기준이면 /references/returns-faq.md, 파일 기준이면 ../references/returns-faq.md다. 공식 스킬 okf-generate는 경로 필드를 /로 시작하게 쓰라고 안내한다.

모범 답안: checkAttribution과 trace (테스트를 직접 통과시킨 뒤에 열기) 
export function checkAttribution(p: ConceptProvenance): AttributionIssue[] {
  const ids = new Set(p.sources.map((s) => s.id).filter((id) => id !== undefined));
  const issues: AttributionIssue[] = [];
  const seen = new Set<string>();
  for (const c of p.claims) {
    for (const label of c.labels) {
      if (ids.has(label) || seen.has(label)) continue;
      seen.add(label);
      issues.push({ kind: 'unknown-label', message: `${p.path} ${c.line}행의 각주 [^${label}]에 맞는 sources id가 없다.` });
    }
  }
  p.sources.forEach((s, i) => {
    if (!s.resource) issues.push({ kind: 'missing-resource', message: `${p.path}의 sources ${i + 1}번째 항목(${s.id ?? 'id 없음'})에 resource가 없다.` });
  });
  return issues;
}

export function trace(bundle: Bundle, path: string, visited: Set<string> = new Set()): TraceNode | null {
  const p = readProvenance(bundle, path);
  if (p === null) return null;
  visited.add(path);
  const sources = p.sources.map((s): TraceSource => {
    const base = { id: s.id, resource: s.resource };
    if (!s.resource) return { ...base, kind: 'none' };
    const kind = classifyResource(s.resource);
    if (kind !== 'path') return { ...base, kind };
    const { target, legacy } = resolvePathField(bundle, path, s.resource); // '/'는 번들 루트, 아니면 개념 위치 기준
    const at = legacy ? { ...base, legacy } : base;
    if (target === null) return { ...at, kind: 'outside' };
    if (!bundle.has(target)) return { ...at, kind: 'missing', target };
    if (!isConceptPath(bundle, target)) return { ...at, kind: 'not-a-concept', target };
    if (visited.has(target)) return { ...at, kind: 'bundle', target };
    return { ...at, kind: 'bundle', target, next: trace(bundle, target, visited) ?? undefined };
  });
  return { path, claims: p.claims, sources, issues: checkAttribution(p) };
}

v0.2 기준 답안과 다른 곳은 두 가지다. 하나는 resolveLink 대신 resolvePathField를 써서 v0.2 번들의 대체 해석 결과(legacy)까지 받는 것이다. 다른 하나는 대상 파일이 있어도 개념이 아니면 not-a-concept로 나누고 따라가지 않는 것이다.

# 반품·환불 FAQ

**Q. 언제까지 반품을 신청할 수 있나요?**
상품을 받은 날부터 7일 이내에 신청할 수 있습니다. 할인 상품도 같습니다.

**Q. 반품할 수 없는 상품이 있나요?**
주문할 때 최종 판매로 표시된 상품은 반품할 수 없습니다.

**Q. 환불은 언제 되나요?**
반품이 승인되면 영업일 기준 3~5일 안에 환불됩니다.

5. 검토

  • 출처가 있다고 맞는 것은 아니다. 출처는 "무엇을 보고 썼나"만 말한다. 정책 문장이 FAQ와 정말 같은지 누가 확인했는지는 적혀 있지 않다. 그것은 verified가 맡는다.§5.2 0008에서 다룬다.
  • 계보는 FAQ에서 끝난다. FAQ 개념에는 sources가 없다. 더 거슬러 올라갈 자료(예: 내부 규정 문서 URL)가 있다면 FAQ에도 출처를 달 수 있다.
  • 원문 개념도 개념이다. references/ 안의 파일도 type을 가진 개념이라서 검증기도 검색기도 똑같이 읽는다. 거꾸로 type이 없는 .md(예: references/README.md)는 v0.3에서 개념이 아니다. 검증기는 not-a-concept 경고만 내고, 검색기는 건너뛰고, trace는 not-a-concept로 표시하고 따라가지 않는다.§3.2 6단계에서 본 변화가 그 결과다. 무엇을 근거로 쓸지는 소비자가 type을 보고 정한다.

완료 기준 (학습 계획 §6 심화 1)

  • pnpm test의 P단계 통과.
  • references/returns-faq.md가 있고, returns.md의 sources·각주가 그 개념을 가리킨다. pnpm validate 오류 0개.
  • 답변 → 정책 → FAQ를 따라가 같은 사실을 확인했다.
  • sources[].resource 경로 형식을 팀 규칙에 기록했고, FAQ 개념이 검색에 준 영향을 evaluation.md 7회차에 적었다.

6. 다음 회차 시작 질문

  1. FAQ 개념이 검색에서 정책 개념을 밀어낸 이유를 말하고, type으로 그것을 막는 방법을 하나 든다.
  2. 정책 문장과 FAQ가 같다는 것을 사람이 확인했다. 그 사실은 개념의 어디에 적는가?
  3. FAQ가 고쳐지면 정책 개념이 낡았다는 것을 소비자가 어떻게 알 수 있을까?
